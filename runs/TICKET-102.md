## 1. Ticket
parse_version in versions.py splits on '.' and calls int() on each part, so Debian version strings with an epoch (1:) or revision suffix (-1ubuntu1) raise a raw ValueError. This crashes the dry-run check from cli.py via plan_remediation and is_vulnerable. The fix is to parse Debian-style versions safely, compare them correctly, and raise InvalidVersionError for malformed input.

- **[minor] error_handling** `src/remediator/versions.py`: In parse_version, the marker is computed as `-1 if "~" in upstream[match.end():]`. That check looks at the whole suffix, but _SUFFIX also allows '~' inside the '+' part (`\+[0-9A-Za-z.+~]+`). So '2.61.0+dfsg~1' is classed as a pre-release and reported VULNERABLE against 2.61.0. The plan says a '+' suffix is ignored, and dpkg also orders it above 2.61.0. The error is a false positive (it over-reports, which is the safe direction), but it contradicts the stated decision. Suggestion: Use capture groups in _SUFFIX, e.g. `(?P<tilde>~[0-9A-Za-z.]+)?(?P<plus>\+[0-9A-Za-z.+~]+)?`. Set marker = -1 only when the 'tilde' group matched. Add a case to test_is_vulnerable_tilde_prerelease_older_than_release: is_vulnerable('2.61.0+dfsg~1', '2.61.0') is False.
- **[minor] error_handling** `src/remediator/versions.py`: AC4 says a raw ValueError must never escape. Python 3.11's integer string-conversion limit (4300 digits) means `int(part)` in parse_version, and `int(epoch)` in _split_epoch, still raise a raw ValueError for a pathological component of more than 4300 digits. Separately, `\d` matches any Unicode decimal digit, so non-ASCII digits such as '٢.٥' are accepted. Both inputs are unlikely from dpkg-query, but STANDARDS.md requires external input to be validated. Suggestion: Use `[0-9]` (or re.ASCII) in _NUMERIC and _EPOCH, and cap component length (e.g. `[0-9]{1,9}`). Alternatively, wrap the int conversions and re-raise as InvalidVersionError (`raise InvalidVersionError(...) from exc`).
- **[minor] readability** `src/remediator/versions.py`: The comment at the end of parse_version ('a pre-release must sort before any further component, so use a sentinel layout...') is hard to follow. Other details are also undocumented:
- The trailing-zero trim, the marker placement and why the encoding orders correctly are not described in the docstring.
- The Version alias is still the generic `tuple[int, ...]` with no description of its layout.
- The revision regex is compiled inline in _strip_revision rather than as a module constant like the others. Suggestion: Replace the comment with a short, precise explanation, e.g. 'Layout: (epoch, *upstream_numbers_without_trailing_zeros, marker); marker is -1 for ~pre-release, 0 otherwise, so a pre-release sorts before the release and before any longer version.' Add a comment documenting the Version layout. Move the revision pattern to a module-level `_REVISION` constant.
- **[minor] tests** `tests/test_versions.py`: Two tests depend on the internal tuple layout instead of observable behaviour:
- test_parse_version_simple asserts `parse_version('2.61.0')[1:3] == (2, 61)`.
- test_parse_version_epoch_is_parsed asserts `[0] == 1`.

Separately, test_is_vulnerable_plain_versions_unchanged only checks 2.9.0 < 2.61.0, which test_is_vulnerable_compares_numerically already covers, so it adds little. Suggestion: Express these tests as comparisons, e.g.:
- parse_version('1:2.58.0') > parse_version('2.99.0')
- parse_version('2.61.0') == parse_version('2.61')

In the plain-versions test, assert ordering across several pairs or a sorted() list, e.g. ['2.9.0', '2.10.0', '2.61.0', '2.61.1', '3.0'], to show AC5 more convincingly.
- **[info] maintainability** `src/remediator/versions.py`: These comparison semantics are not pinned by tests:
- Pre-release tags compare equal, so 2.61.0~rc1 == 2.61.0~rc2.
- Revisions are ignored, so 2.61.0-1 == 2.61.0-2.
- A Debian upstream containing '-' (e.g. '1.2-3-1') or letters (e.g. '2.58.0a') now raises InvalidVersionError.

All of these follow the approved decisions and listed risks, but they are only described in the implementer notes. Suggestion: Add one or two tests that pin these behaviours, e.g. parse_version('2.61.0~rc1') == parse_version('2.61.0~rc2'), and pytest.raises(InvalidVersionError) for '2.58.0a'.
