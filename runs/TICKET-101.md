## 1. Ticket
Add dnf support to remediator so RHEL-family hosts (RHEL, Rocky, Amazon Linux, Fedora, CentOS) are detected, queried for installed versions via rpm, and patched with dnf, while keeping dry-run as the default and leaving apt behaviour unchanged.

## 2. Acceptance criteria
- **AC1** Hosts whose /etc/os-release ID or ID_LIKE contains rhel, fedora, centos or amzn are detected as using dnf.
- **AC2** The installed version is read with `rpm -q --qf %{VERSION} <package>`; a non-zero exit code means 'not installed'.
- **AC3** The upgrade command for dnf is `dnf upgrade -y <package>`, built as an argument list.
- **AC4** Dry-run remains the default; nothing is executed without --apply.
- **AC5** Unsupported platforms still raise UnsupportedPlatformError, and the message lists every supported package manager.
- **AC6** Existing apt behaviour is unchanged and all existing tests still pass.
- **AC7** New tests cover detection, the version query, and the upgrade command for dnf.

### Risks
- Substring or token matching mistakes could misclassify hosts, for example a host with both apt and dnf tokens. Whole-token matching and apt-first ordering are pinned by tests.

- RPM versions may contain characters such as '~' or '^' that versions.py may not parse. Such a version raises InvalidVersionError and the CLI exits 2 rather than crashing.

- **[minor] standards** `README.md`: The approved plan lists a README.md change: document that apt and dnf (RHEL-family) hosts are supported and that dry-run remains the default. The diff does not touch README.md, so the user-facing docs still describe an apt-only tool. AC4 itself is still met in code and tests, but the planned documentation is missing. Suggestion: Add a short 'Supported platforms' section listing apt (Debian/Ubuntu) and dnf (RHEL/Fedora/CentOS/Amazon Linux, detected via ID/ID_LIKE). State that nothing changes on the host without --apply. Alternatively, record in the PR why the README change was dropped.
- **[minor] error_handling** `src/remediator/platforms.py`: detect_package_manager maps any 'amzn' or 'centos' ID to dnf. However, Amazon Linux 2 (ID="amzn", VERSION_ID="2") and CentOS/RHEL 7 ship yum and usually lack a dnf binary. On those hosts the rpm query in dry-run works, but `--apply` would try to execute ['dnf','upgrade','-y',pkg] and fail. Depending on how the real CommandRunner handles a missing executable, the user may see FileNotFoundError or an unclear failure rather than a clean UnsupportedPlatformError. This follows the ticket's mapping literally, so it is not a defect against the ACs. It is, however, a fleet-level risk the ticket's 'whole fleet' goal implies. Suggestion: Call this out as a known limitation in the PR and README. Consider a follow-up ticket to either detect yum-only hosts via VERSION_ID or fall back to `yum upgrade -y`. Also confirm the runner converts a missing executable into a specific errors.py exception rather than a traceback.
- **[minor] error_handling** `src/remediator/platforms.py`: The format `rpm -q --qf %{VERSION} <pkg>` has no trailing newline. For packages with multiple installed instances (multilib i686+x86_64, or installonly packages), rpm prints the versions concatenated, e.g. '2.58.02.58.0'. That string reaches versions.py, which will most likely raise InvalidVersionError, so the CLI exits 2 instead of reporting a result. The plan documents that downstream validation turns this into exit 2 rather than a crash, so this is safe but unhelpful. Suggestion: Keep the command exactly as specified by AC2. Add a regression test, e.g. test_cli_dnf_concatenated_rpm_output_exits_2, so the behaviour is pinned. Consider a follow-up ticket to use '%{VERSION}\n' and validate that all lines agree.
- **[minor] tests** `tests/test_remediate.py`: test_plan_remediation_dnf_non_zero_exit_is_not_installed fakes rpm returning rc=1 with 'not installed' on stderr. Real rpm prints 'package acme-cli is not installed' on stdout. The test still passes because inventory keys on the return code, but the fixture does not reflect the real output. It would not catch a regression where non-empty stdout with rc=1 is treated as a version. Suggestion: Use CommandResult(1, "package acme-cli is not installed", "") to mirror real rpm output. This pins the 'non-zero exit means not installed regardless of stdout' contract from AC2.
- **[minor] tests** `tests/test_remediate.py`: The dnf tests cover only the vulnerable and not-installed paths. There is no dnf equivalent of test_plan_remediation_safe_version_returns_none, and no check that plan_remediation on dnf calls only the rpm query and never runs the upgrade, as test_plan_remediation_never_runs_upgrade_itself does for apt. The ACs do not strictly require these tests. Suggestion: Add test_plan_remediation_dnf_safe_version_returns_none (rpm returns '2.61.0', action 'none', command None). Optionally assert runner.calls == [list(RPM_QUERY)] in the dnf vulnerable test.
- **[info] maintainability** `tests/test_cli.py`: The command-tuple constants are duplicated between test_cli.py and test_remediate.py: DPKG_QUERY and RPM_QUERY in both, and DNF_UPGRADE alongside an inline dnf list. FakeRunner keys on exact tuples, as the plan's risk section notes, so a drift between copies would cause confusing false 'not installed' results. Suggestion: Move the query and upgrade tuples into conftest.py next to the OS-release constants, and import them in both test modules.
- **[info] maintainability** `src/remediator/platforms.py`: Each package manager is now spread across three parallel if-chains: the detect sets, build_installed_version_command and build_upgrade_command. This is fine for two managers and complies with STANDARDS (all in platforms.py), but each new manager such as zypper will need edits in three places. Suggestion: Optionally, in a later refactor, use a single registry dict mapping manager to (distro ids, version-query builder, upgrade builder) that is ordered so apt is checked first. This is not needed for this ticket.
